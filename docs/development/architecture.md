# アーキテクチャ規約

この文書は、Flutter / Dart アプリケーションの構成、責務分離、状態管理、データアクセス、UI / Widget 設計に関する規約を定める。実装時は [`AGENTS.md`](../../AGENTS.md) と、この変更に関係する [`docs/feature/`](../feature/) のドキュメントも確認する。

## feature 単位の設計

アプリケーションは原則として feature 単位で構成する。画面、状態管理、ドメインロジック、データアクセスなどをアプリ全体で種類別にまとめるのではなく、可能な限り関連する feature の配下に配置する。

feature 間で共有するものだけを共通領域へ配置する。将来共有される可能性だけを理由に、最初から共通化しない。feature 間の循環依存を作らず、特定 feature の内部実装を別 feature から直接参照する構造は可能な限り避ける。

feature 名は技術的な名前ではなく、ユーザーまたはドメイン上の機能を表す名前にする。feature が単純な場合は、空の `domain/` や `data/`、不要な階層を形式的に作成しない。規模が大きくなった場合は、責務に応じて feature 内を追加分割するが、最初から将来を想定した深いディレクトリ構造にはしない。

## ディレクトリ構成

基本構成は以下を基準とする。

```text
lib/
  app/
    app.dart
    router/
    theme/

  core/
    error/
    network/
    storage/
    utils/

  shared/
    widgets/

  features/
    <feature_name>/
      presentation/
        <feature_name>_page.dart
        widgets/
      domain/
      data/

  main.dart

docs/
  development/
  feature/

test/
```

* `app/` にはアプリ全体の起動・ルーティング・テーマなど、アプリケーション全体に関係する処理を配置する。
* `features/` には機能単位のコードを配置する。
* `presentation/` には Page、Widget、状態管理など UI に直接関係するコードを配置する。
* `domain/` には必要に応じてドメインモデル、Repository の抽象、UseCase 等を配置する。
* `data/` には Repository の実装、API Client、Data Source、DTO 等のデータアクセスに関係するコードを配置する。
* `core/` には特定 feature に属さないアプリ基盤を配置する。
* `shared/` には複数 feature から実際に利用される共有 UI 等を配置する。
* 1つの feature でしか使用しないものを `core/` や `shared/` に配置しない。
* `utils/` を汎用コードの置き場所として乱用しない。より具体的な責務を表すディレクトリへ配置できる場合はそちらを優先する。

## 責務分離

UI、状態管理、ビジネスロジック、データアクセスの責務を分離する。Widget にビジネスロジックや直接的なデータアクセス処理を過度に持たせない。

Service、Manager、Helper、Util など責務が曖昧になりやすいクラスを安易に作成しない。より具体的な責務として表現できる場合は、その責務に応じたクラス名・構造を使用する。

## UI / Widget 設計

UI は、画面単位の Widget、複数画面で共通利用する Widget、画面内でのみ利用する部分 Widget を適切に分離する。

画面全体の Widget は画面全体の構成、状態管理との接続、画面遷移との接続を主な責務とし、再利用可能な UI 部品や複雑な表示ロジックを過度に持たせない。

BottomNavigationBar / NavigationBar、共通 AppBar、共通レイアウトなど、複数画面にまたがって常時表示・管理される UI は、各画面へ重複して実装せず、原則としてそれらを管理する親 Widget または共通 Widget に分離する。

ボタン、カード、入力欄など、複数箇所で利用する UI やデザイン統一が必要な UI は共通 Widget として分離する。1画面内でのみ利用する UI でも、コード量が大きい、独立した責務を持つ、または可読性が低下する場合は部分 Widget に分離する。

一度しか利用せず、単純で短い UI を機械的に別ファイルへ分割しない。過度なコンポーネント化を避け、コードの追いやすさを優先する。

Widget を分離する場合は、必要な値やコールバックを引数として受け取り、可能な限り親画面の状態や具体的な実装詳細へ強く依存しない構造にする。

画面固有の Widget は原則として該当 feature の `presentation/widgets/` に配置する。複数 feature で実際に共有される Widget は `shared/widgets/` に配置する。将来再利用する可能性だけを理由に `shared/widgets/` へ移動しない。

Widget の `build` メソッド内に複雑なデータ変換、ビジネスロジック、副作用を記述しない。API 通信、ストレージ操作などのデータアクセスを Widget から直接実行しない。

## 状態管理

状態管理方式はプロジェクト全体で統一し、同じ目的で複数の状態管理方式を混在させない。状態管理ライブラリを採用した後は、そのライブラリの推奨パターンとプロジェクト内の既存パターンに従う。特定のライブラリや方式を、既存方針を確認せず新たに選定しない。

Widget ローカルで完結する一時的な UI 状態まで、不要にグローバルな状態管理へ移さない。複数 Widget や画面間で共有する必要がない単純な UI 状態は、必要に応じて Widget 内で管理する。

状態管理層に `BuildContext` や具体的な Widget への依存を持ち込まない。API 通信やデータ取得の結果だけでなく、必要に応じて loading、success、empty、error 等の状態を明確に扱う。エラーを握りつぶさず、UI での表示が必要なエラーと開発者向けのエラーを適切に区別する。

## Repository、API Client、Data Source

Repository はデータ取得・保存などのデータアクセスを抽象化する責務を持つ。Repository と API Client / Data Source の責務を混在させない。

API Client、Data Source 等を設ける場合は、HTTP 通信やローカルストレージなど具体的なデータソースとの通信を担当させる。API 通信処理を Page や Widget に直接記述しない。

Repository の利用側が HTTP ステータスコードや通信ライブラリ固有の型へ不必要に依存しない構造を優先する。同じ API やデータソースへのアクセス処理を複数箇所へ重複して実装しない。

エラー処理、タイムアウト、キャンセル等は、採用している通信方式とプロジェクト全体の方針に合わせて一貫して扱う。

## Domain Model と DTO

API の request / response とアプリ内部のドメインモデルを分離する必要がある場合は、DTO と変換処理を用意する。API レスポンスや永続化専用のモデルなど、ドメインモデルと区別する必要があるデータモデルには、役割が分かる名前を使用する。

JSON の key やバックエンド固有の仕様を UI 層へ漏らさない。

## 共通化・抽象化

UseCase 層は、ビジネスロジックが複雑で分離する明確なメリットがある場合に導入する。単純な処理に対して形式的に UseCase を作成しない。

抽象化は現在必要な範囲で行い、将来の可能性だけを理由に不要な interface、abstract class、ラッパー層を追加しない。
